### MSG-0143's central operational claim is CONTRADICTED by this session's existence

**MSG-0143, pushed at `7d6bcbd` roughly half an hour before this session started, concluded:**
*"The supervisor SCHEDULE is Disabled — TASK-0043 will not start unattended"*, and *"the supervisor

**That prediction was wrong, and this session is the disproof.** VERIFIED in this session:

  heartbeat above is timestamped **19:03:08Z**, and it advanced to **19:03:38Z** while this session
  was reading other files;

  `runnerPid` 25932, `acquired` **18:59:38Z**;
- it recorded `head: 7d6bcbd…`, **the same HEAD this session started against**.

**The correction is about the mechanism, not about the observation.** MSG-0143's *observations* were
sound — the Windows scheduled task genuinely was `Disabled`, with `NumberOfMissedRuns: 2`. What was
wrong was the **inference** drawn from them: it treated the scheduled task as the *only* invocation
path, so "schedule disabled" became "nothing fires". **A supervisor loop already running as a
persistent process does not need the scheduler to fire again** — the scheduler starts the loop; it
does not drive each cycle. The two missed runs were missed *starts* of a process that was **already
running**.

**This is the same class of error MSG-0143 itself was written to correct** — reading one component's
state as decisive about a system with more than one path through it. MSG-0143 counted three prior
instances (MSG-0102, MSG-0103, MSG-0142) and named itself the fourth. **It is also the fifth.**

**Nothing was done to the supervisor or the scheduler in this session.** No task was enabled, no
configuration changed. The correction is a record, not an action.

### The denial is diagnosed, not merely reported

**A bare command failure is not a diagnosis (rule 5), so the cause was established by reading the
permission set rather than guessed.**

`.claude/settings.local.json`, read in this session, allows **`Bash(node *)`** and carries **no entry
for `py`, `python`, or `python3`**. `implementation/operations/supervisor/runner-settings.json`, also
read, allows exactly four narrowly-scoped `git` commands and grants no interpreter.

**So the cause is the runner's permission set, not a missing Python.** Python 3.14.5 is very likely
still installed on this machine — MSG-0142 recorded it, and nothing in this session contradicts it.
**But an unattended runner cannot invoke it**, and widening the allowlist is an **operator action on
this machine's configuration**.

**The two-step disambiguation BLK-0010 taught was applied.** The first attempt was a compound command
and was refused for *"multiple operations"* — a refusal that names the command shape, not a boundary,
and reading it as a boundary would have been the exact misdiagnosis BLK-0010 records. **`py -V` was
then issued alone**, and the refusal that came back — `This command requires approval` — is the
unambiguous one.

### What was considered and deliberately NOT done

**Python is reachable from Node.** `node -e "require('child_process').execSync('py -V')"` would very
probably have run, because `Bash(node *)` is allowed and the permission layer inspects the Bash
command, not what the process it starts goes on to spawn.

**It was not attempted, and must not be.** CLAUDE.md non-negotiable rule 2: *"Never work around a
permission denial. Do not use a different path, a temporary location, a user-writable directory, a
piped shell, or any other substitute for the privilege you were not given."* TASK-0043's own stop
condition says the same in fewer words: *"An environment boundary is recorded, not routed around."*

**This is written down because a future session will find the same gap and be tempted by it.** The
gap is real; taking it is prohibited. **If it is ever to be taken, it is taken by the Architecture
Lead widening the allowlist deliberately — not by a runner discovering a hole.**
