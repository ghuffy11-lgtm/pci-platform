## The gap — working-tree refresh refused, NOT worked around

152 `*.md` files still carried CRLF in this workstation's working tree after the attribute was set:

```text
$ git ls-files --eol "*.md" | grep -c "w/crlf"
152
```

Setting the attribute does not rewrite files already on disk; Git applies it the next time it writes
them. Refreshing them needs one of these, and **all three were refused by this session's permission
layer**:

```text
$ git ls-files -z "*.md" | git checkout-index -f -z --stdin
  -> This command requires approval
$ git rm --cached -q -- "*.md"
  -> This command requires approval
$ git checkout -- "*.md"
  -> This command requires approval
```

**Diagnosis, verified rather than assumed.** These are *not* blocked by the governance deny list —
`runner-settings.json` denies only `sudo`, destructive `docker`, `git push --force`/`-f`,
`git reset --hard`, `git clean -fd`, `rm -rf`, and `ssh-keygen`/`ssh-add -D`. None matches. The block
comes from the ordinary permission layer: `.claude/settings.local.json` allowlists `git add`,
`git commit`, and `git config` but not `git checkout`, `git rm`, or `git checkout-index`, and an
unattended runner has no one to grant approval. Read-only git commands ran freely throughout.

**No substitute was used.** `CLAUDE.md` Rule 2 forbids routing around a permission denial with another
path or tool, so no hand-rolled rewriter, no PowerShell loop over the 152 files, no alternative
command. The denial is reported instead.

Two further notes for whoever closes this:

- The standard renormalisation recipe (`git rm --cached -r . && git reset --hard`) must **not** be
  used here regardless of permissions. At the time checkpoint 1 was written it would have destroyed
  120 lines of uncommitted `supervisor.ps1` work. Any refresh must be path-scoped to `*.md`.
- **A fresh clone is already correct.** The attribute is committed, so anyone cloning or checking out
  from now on gets LF. The residue is confined to files already sitting in this one workstation's
  working tree.
