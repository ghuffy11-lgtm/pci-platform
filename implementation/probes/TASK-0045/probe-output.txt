==============================================================================

  "a fact about the configuration, not about the criterion" -- that
  run was in WAL mode, where no rollback journal is used.  This
  section puts the subject in the configuration that DOES use one.
  journal_mode:                                      delete
  maintenance state:                                 none -- no checkpoint applies in this mode

  --- F1  AFTER INGEST, no transaction open -- the per-transaction baseline -
    (main db)     PRESENT, 32768 bytes:              UNAUTH x235  AUTH x235
    -wal          NEVER CREATED:                     (no file to scan)
    -shm          NEVER CREATED:                     (no file to scan)
    -journal      NEVER CREATED:                     (no file to scan)
  baseline: does a -journal exist before any transaction: NEVER CREATED
  => a -journal seen later was CREATED by the transaction: YES -- attribution available at artefact level

  --- F2  A write whose provenance is INGEST -- maintaining the projection --
      This transaction adds approved-corpus rows.  It is NOT a
      request being resolved for any subject.
    -journal      PRESENT, 4616 bytes:               UNAUTH x26  AUTH x26

      DA-4 ROW 1: written at ingest, maintaining the projection of
      approved content => NOT a DA-1.1 or DA-1.2 finding, however
      many times the marker appears.  ADR-0020 §1 governs it.

  --- F3  Request-resolution write #1 -- the caching shape (APPENDS) --------
      A retrieval layer that caches its working set writes back what
      it examined, into a NEW table.  Nothing is ingested here: every
      byte written is a consequence of resolving the request.
    -journal      PRESENT, 8720 bytes:               UNAUTH x0  AUTH x0

      MEASURED, AND NOT WHAT THE PROBE'S AUTHOR EXPECTED.  The marker
      count above is what it is; if it is 0, the reason is structural:
      a rollback journal holds the ORIGINAL images of pages about to
      be OVERWRITTEN, and rows appended into fresh pages overwrite
      nothing.  An APPEND-shaped request-induced write therefore need
      not journal any corpus content at all.
      Under DA-5 row 3 this absence is NOT sufficient and NOT a pass.

  --- F4  Request-resolution write #2 -- access accounting (OVERWRITES) -----
      The other everyday retrieval-layer write: record that a chunk
      was served.  It UPDATES rows in the shared projection itself,
      and it updates ONLY rows the subject was ENTITLED to receive.
    -journal      PRESENT, 33344 bytes:              UNAUTH x236  AUTH x235

  --- F5  AFTER COMMIT ------------------------------------------------------
    -journal      NEVER CREATED:                     (no file to scan)

  THE SHARPEST RESULT IN THIS SECTION.  The request updated ONLY
  rows the subject was entitled to -- and the rollback journal came
  back holding the UNAUTHORIZED marker 236 times.  The engine
  journals whole PAGES, and a page holding an authorized row also
  holds its unauthorized neighbours.  So a write touching nothing
  the subject was forbidden still made forbidden content durable.
  DA-4 row 2: it happened BECAUSE the request was resolved.
  DA-5 row 1: a single occurrence is sufficient => NOT CLEARED.

  Note what this does NOT depend on: no post-filtering, no bad query
  plan, and no examination of unauthorized rows by the request. This
  is page granularity, not query shape -- so §4.13 N1 containment,
  which works by keeping unauthorized content out of REACH, is the
  kind of answer it responds to, and a better query is not.

  AND THE DA-4 CONTRAST, which is why the section is built this way:
    F2 ingest write -- marker in journal:            26 times
    F2 verdict:                                      NOT a DA-1 finding -- DA-4 row 1, ingest provenance
    F4 request write -- marker in journal:           236 times
    F4 verdict:                                      DA-1.1 FINDING -- DA-4 row 2, request provenance
  The two observations are the same SHAPE and get opposite answers.
  A criterion phrased as PRESENCE would have flagged both, failed the
  engine on the ingest one, and told nobody anything.  That is what
  §4.16 DA-4 was written to prevent, demonstrated on this run's own
  output rather than argued.

  READ F5 CAREFULLY.  "NEVER CREATED" does NOT mean the artefact never
  held the content -- F2 and F4 measured that it did.  It means the
  artefact was reclaimed between the inspections.  §4.16 DA-5 row 3
  names this exactly: "an absence proves only that nothing crossed the
  point, and the moment, at which the inspection was taken.  An
  artefact may have been checkpointed, truncated, rotated or reclaimed
  between the request and the scan."  A probe that scanned only AFTER
  the request would have reported a clean result here, and it would
  have been a FALSE NEGATIVE.
