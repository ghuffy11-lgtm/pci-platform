SECTION 3 — GAP 2: U1, INDEX-ENTRY EXAMINATION. Why the prior zero was a row-access zero.
============================================================================================================
EPA-0006 §4.6 S4 counts U1 — "reads an index entry or key during traversal" — as examining, and
§4.7 Q1's fail-closed default keeps that reading until ruled. MSG-0118 recorded that U1 is not
instrumentable through node:sqlite. MSG-0120 forbids reporting U1 = 0 on that basis.

3.1 — The direct instrument is absent, and its absence is now a checked fact.

  SQLITE_ENABLE_STMT_SCANSTATUS: ABSENT (section 2.2).
  sqlite3_stmt_scanstatus() is the API that reports, per loop, the number of index entries
  visited. It is the instrument that would settle U1 outright. It is not compiled in, and
  node:sqlite binds no accessor for it in any case. BOTH would have to change.

3.2 — What the engine itself shows about WHERE a row-access counter sits.

  The bytecode below is the ACTUAL EXPLAIN output for the shape of K8's bounded limb. It is
  engine-reported, not a description of what SQLite is believed to do.

      0  Init           p1=  0 p2= 17 p3=  0             
      1  OpenRead       p1=  0 p2=  2 p3=  0 4

      3  Integer        p1=  0 p2=  1 p3=  0

     18  Integer        p1=1000 p2=  4 p3=  0             
     19  Goto           p1=  0 p2=  1 p3=  0             

  Read it in order. Cursor 1 is the INDEX; cursor 0 is the TABLE.
    SeekGT 1       — seek the INDEX cursor to the start of the range
    IdxGT  1       — range-end test, ON THE INDEX
    DeferredSeek 1 — the TABLE seek is DEFERRED. No row has been fetched yet.
    Column 1 2     — read eff_from FROM THE INDEX CURSOR (cursor 1)
    Gt     -> Next — FAILS THE RESIDUAL AND JUMPS STRAIGHT TO Next.
                     The entry was visited. The table row was never touched.
    Column 0 0     — only reached by entries that PASSED. This is where probe_ver fires.

  THAT IS THE WHOLE FINDING, AND IT IS THE ENGINE'S OWN BYTECODE SAYING IT: a counter written
  into the WHERE clause on a NON-INDEXED column cannot fire for an entry the residual rejects,
  because the row is never read. EPA-0006 §4.6 S5 predicted exactly this — "a zero count proves
  only that nothing unauthorized crossed the point where the instrument sits" — and here it is
  demonstrated at opcode level rather than argued.

SECTION 4 — A NEW INSTRUMENT, AND ITS CALIBRATION AGAINST KNOWN TRUTH
============================================================================================================
open_ended is the LEADING column of BOTH candidate indexes, so a function applied to it is
evaluated FROM THE INDEX CURSOR, before the deferred table seek. It therefore fires once per
index entry visited inside the seek range.

IT IS A LOWER BOUND ON U1. It does not see interior b-tree pages descended during the seek,
pager reads, or any other loop. A POSITIVE VALUE IS CONCLUSIVE OF FAILURE (§4.6 S5); NO VALUE
OF IT MAY BE READ AS U1 = 0, AND THIS PROBE NEVER SO READS IT.

Calibration: a fixture whose in-range entry count is known BY CONSTRUCTION, run on BOTH
candidate plans. If the instrument does not reproduce the known number exactly, it is not
trustworthy and nothing below may rest on it.

  Constructed cohort: expired=300 (eff_to closed), notYetBounded=400 (eff_from future), authorized=2

  PLANNER CHOICE    plan: SEARCH cv USING INDEX i_cal_vo (open_ended=? AND eff_from<?)
      index-cursor calls =   302   expected by construction =   302   EXACT — instrument TRUSTWORTHY
      row-access calls   =   302   rows returned = 2
      -> the LOWER bound is the seek; the other bound is a residual, and the 300 unauthorized entries it rejects were  row-accessed

  PINNED  i_cal_vb  plan: SEARCH cv USING INDEX i_cal_vb (open_ended=? AND eff_to>?)
      index-cursor calls =   402   expected by construction =   402   EXACT — instrument TRUSTWORTHY

  CALIBRATION PASSED on both plans. The instrument reproduces the constructed count exactly,
  and it reproduces it under BOTH index choices — so it is not measuring one plan's artefact.

  Note the row-access column in the pinned case. The design that examined 402 index entries
  reported 2 row accesses. THAT IS THE SHAPE OF TASK-0038's K8 RESULT, reproduced on a
  fixture small enough to check by hand.

SECTION 11 — FINDINGS. Each one is arithmetic on the tables above, not commentary.
============================================================================================================
F1. K7 AND K8 VISIT THE SAME NUMBER OF ENTRIES. `U` SEES ONE AND NOT THE OTHER.

             M   K7 Nidx   K8 Nidx     K7 U     K8 U
            50        10        10        7        0
           500        74        74       71        0
          5000       717       717      714        0
         20000      2860      2860     2857        0

    Nidx identical at every size: YES. The two designs traverse the same
    number of index entries; they differ only in WHICH BOUND is the seek, and therefore in
    whether the unauthorized entries are rejected FROM THE INDEX (invisible to a row-access
    counter) or AFTER A ROW READ (visible to it).

    TASK-0038 reported K7 U=715 and K8 U=0 at M=5000 and called that the sharpest result in
    the table. IT WAS CORRECTLY MEASURED AND IT MEANT SOMETHING NARROWER THAN IT LOOKED:
    K8 did not examine less. It examined the same amount somewhere the instrument could not
    see. MSG-0118 said as much in its result 4 and could not measure it; this run measures it.

F2. `ANALYZE` ALONE DRIVES K7's U FROM 2857 TO 0 — AND CHANGES NOTHING ELSE.

    ANALYZE is an ordinary, supported maintenance operation. It writes statistics. It does
    not touch the schema, the data, the indexes, the query text or the design. After it,
    K7's planner switches the populated partition's bounded limb from the LOWER-bound index
    to the UPPER-bound one — becoming, in the only respect that matters here, K8.

    U:    2857 -> 0        (the row-access counter goes quiet)
    Nidx: 2860 -> 2861     (the traversal visits ONE MORE entry, not fewer)

    A candidate measured before a routine ANALYZE and one measured after would receive
    OPPOSITE `U` readings for THE SAME DESIGN. On this engine `U` is not a property of the
    design; it is a property of the statistics table.

F3. E1 SPLITS INTO A LIMB THAT IS PLAN-INDEPENDENT AND A LIMB THAT IS NOT.

    REACHABLE STRUCTURES — plan-independent, and OBTAINED. The authorizer enumerates every
    structure the statement can read, at compile time, before any plan choice. For K7 and K8
    it reports only routed partitions and no scope-spanning structure, and it reports the
    same set under every configuration. It is a SUPERSET of what any plan opens, which is the
    fail-closed direction: what it excludes, no plan can reach.

    CONFINEMENT — NOT plan-independent. K7 produced 2 distinct version traversals and
    K8 produced 2, across configurations that are all ordinary engine states. INDEXED BY
    pinned the bounded limb and did NOT pin the rest: K8's open limb still became a full
    partition scan after ANALYZE. Pinning one limb pins one limb.

    So the honest position is: the "which structures" half of E1 can be evidenced without
    trusting a single plan observation, and the "how much is traversed" half cannot — not on
    this engine, and not by any instrument reachable from it.

F4. THE ONE INSTRUMENT THAT WOULD SETTLE U1 IS A BUILD FLAG AWAY, AND THAT IS A SELECTION
    CRITERION RATHER THAN A DEFECT. `sqlite3_stmt_scanstatus` reports per-loop visit counts
    directly. It requires SQLITE_ENABLE_STMT_SCANSTATUS at compile time (ABSENT here) AND a
    binding in node:sqlite (ABSENT here). EPA-0006 §4.6 S10 already holds that an engine which
    cannot be observed fails the burden AMD-01 places on it. This run is a worked example of
    that rule biting: not "the engine examined too much" but "the engine cannot be asked".
    Recorded as evidence, NOT as a recommendation to select any engine or build option.
